[2026-08-21] Added Telegram bot alerting to the Setup Wizard and vault
  dashboard's Environment Check (it already existed in Super-Admin's
  Policies & Content page and services/adminAlert.js, but
  TELEGRAM_BOT_TOKEN was missing from scripts/lib/envGroups.mjs
  entirely, so it was invisible to both the wizard and the "is it set
  up yet" checkers). Added a `telegram` env group (TELEGRAM_BOT_TOKEN,
  optional) with fix instructions; added a no-side-effect
  verifyTelegramBotToken() live check (Telegram's getMe endpoint) to
  services/telegram.js and wired it into services/envCheck.js so it
  surfaces automatically on the vault dashboard's Environment Check;
  added the group to RemainingEnvStep.jsx's Step 4 checklist (Setup
  Wizard) and to ApiSetupGuideSection.jsx's static guide (vault
  dashboard), with matching step-by-step BotFather setup instructions
  in both places; added the group to remaining-env-status/route.js's
  checked list. Investigated the PDF invoice + Messenger sequencing
  flow (services/invoicePdf.js, BookingFormClient.jsx,
  ReservationSummaryClient.jsx, TourReservationSummaryClient.jsx) and
  found it already fully implemented — no changes made there pending
  clarification of what specifically needs continuing.

[2026-08-28] Added a Gatekeeper 3 pre-lockdown email-OTP challenge
  (docs/gatekeeper-3-otp-challenge.md) so an anomalous-but-correct-
  password login (new device or impossible travel) no longer fires
  the full breach response immediately -- a 6-digit code is emailed
  to VAULT_OWNER_EMAIL first, and the login stays pending for 3
  minutes. Gatekeeper 3 still fires exactly as before if the code is
  wrong, exhausted, or the window expires unanswered. New Prisma
  model LoginAnomalyChallenge; new services/loginAnomalyOtp.js and
  services/loginSession.js (session-cookie helpers extracted so both
  the normal login route and the new OTP-verify route build sessions
  identically); new sendLoginAnomalyOtpEmail() in services/emailAlert.js;
  new app/api/auth/login-otp/verify and .../expire routes; login page
  (app/superAdmin/login/page.jsx + Login.css) now shows a code-entry
  screen with a live countdown while a challenge is pending. Also
  fixed a pre-existing bug in services/breachResponse.js where
  triggerGatekeeperBreach()'s skipIpBlock parameter was accepted but
  never actually read, so the owner-IP leniency it was meant to grant
  never worked -- now honored.

[2026-08-28] Fixed the Gatekeeper 3 OTP challenge from the previous
  entry: it had rendered the code-entry form inline on the same
  /superAdmin/login page instead of as its own route, unlike the
  vault's own passphrase -> /otp page handoff pattern. Now
  app/api/auth/login/route.js sets a "loginOtpChallenge" HttpOnly
  cookie (mirroring vault's "vaultSession" cookie) instead of
  returning challengeId/expiresAt in the JSON body; new Server
  Component app/superAdmin/login/otp/page.jsx reads that cookie and
  redirects back to /superAdmin/login if it's missing/invalid; new
  app/superAdmin/login/otp/LoginOtpClient.jsx holds the actual
  code-entry form + countdown (moved out of page.jsx entirely); new
  LoginOtp.css holds the two OTP-specific classes previously added to
  Login.css. Both login-otp/verify and login-otp/expire routes now
  also clear the cookie once a challenge resolves.
