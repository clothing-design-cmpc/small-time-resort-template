=== PROJECT: Villa Azure Resort ===

1. PROJECT NAME & PURPOSE
Villa Azure Resort is a private resort web application. Current phase
scaffolds the VISITOR master template (public-facing site) first, with
a SUPER ADMIN account to be scaffolded next. The visitor site follows
the section order defined in the resort visitor master template plan:
Hero, About, Rooms & Villas, Amenities, Resort Shop (browse-only, no
cart/checkout), Activities/Experiences, Gallery, Testimonials, Location,
Contact/Inquiry, Footer. Events & Functions and Spa & Wellness are
intentionally left out for now.

Progress: Hero (done), About (done). Next: Rooms & Villas.

2. TECH STACK
- Next.js 16.2.x (App Router, Turbopack)
- JavaScript (no TypeScript)
- React 19.2.x
- CSS Modules / plain CSS (no Tailwind)
- axios (installed, for client-side calls to external APIs)
- Backend service: Supabase (connected — @supabase/supabase-js, direct + session pooler)

3. ACCOUNT TYPES
- visitor    — public, no auth required (scaffolded)
- superAdmin — protected, auth required (not yet scaffolded)

4. DATABASE OVERVIEW
Supabase Postgres, schema managed via Prisma (prisma/schema.prisma) --
NEVER the Supabase SQL Editor. Tables: rooms, amenities, store_products,
bookings, admin_profiles. Prisma 7 note: connection URLs are NOT in schema.prisma --
they live in prisma.config.mjs (CLI: db push/generate/seed, uses
DIRECT_URL) and services/prisma.js (app runtime, uses DATABASE_URL via
the @prisma/adapter-pg driver adapter -- Prisma 7 requires an adapter,
plain `new PrismaClient()` with no adapter will throw at runtime).
Workflow: edit schema.prisma -> npx prisma db push -> npx prisma generate.
RLS/policies applied via prisma/enableRls.js (run once after first db
push). Seed data via prisma/seed.js (npx prisma db seed) -- also creates
the super-admin Auth user from SEED_ADMIN_EMAIL / SEED_ADMIN_PASSWORD.
Env keys required: NEXT_PUBLIC_SUPABASE_URL, NEXT_PUBLIC_SUPABASE_ANON_KEY,
SUPABASE_SERVICE_ROLE_KEY, DATABASE_URL, DIRECT_URL (in both .env and
.env.local -- Prisma CLI/config reads .env, Next.js app reads .env.local),
SEED_ADMIN_EMAIL, SEED_ADMIN_PASSWORD.

5. DATA MODELS OVERVIEW
- Room           -- name, slug (unique), description, pricePerNight, capacity, imageUrl, isActive, sortOrder
- Amenity        -- name, description, icon, isActive, sortOrder
- StoreProduct   -- name, description, price, category, imageUrl, isActive, sortOrder
- Booking        -- roomId (optional FK -> Room), guestName, checkInDate, checkOutDate
                    (checkOutDate is exclusive -- standard hotel convention), status
                    (confirmed | cancelled). Powers the Booked Dates section and the
                    Reserve Your Villa date picker -- both read the same
                    GET /api/bookings/dates endpoint instead of a hardcoded date list.
- AdminProfile   -- id (matches a Supabase Auth user UID), fullName, role. The actual
                    email/password for every admin account lives in Supabase Auth's
                    built-in auth.users table (not managed by Prisma); admin_profiles
                    only stores role/profile metadata keyed to that same user id.

8. API ENDPOINTS
- POST  /api/auth/login  — body { email, password }; verifies against
  Supabase Auth + admin_profiles, sets the "session" HttpOnly cookie.
- POST  /api/auth/logout — clears the "session" cookie.
- GET   /api/bookings/dates — public; no input. Returns
  { success, data: { bookedDates: ["YYYY-MM-DD", ...] }, message }.
  Expands every confirmed Booking's [checkInDate, checkOutDate) range
  server-side and returns a deduplicated, sorted list.
- GET   /api/admin/bookings — super-admin only. Returns
  { success, data: { bookings: [...] }, message } — every Booking row
  (confirmed + cancelled) including room.name.
- PATCH /api/admin/bookings/{id} — super-admin only. Sets that booking's
  status to "cancelled". No body required.
- GET   /api/booking-rules — public. Read-only subset of the super-admin's
  BookingRules row (nights range, advance window, enabled booking types,
  tour pricing, deposit %, cancellation terms).
- GET   /api/rooms/{roomId}/availability — public. Returns that room's
  unavailableDates (booked + blackout, merged) plus its capacity/nights bounds.
- POST  /api/bookings/quote — public. Body: { roomId, bookingType,
  checkInDate, checkOutDate, numberOfGuests }. Validates against
  BookingRules + room overrides and returns a price breakdown WITHOUT
  saving anything. Returns 400 with a guest-facing message on any
  rule violation.
- POST  /api/bookings — public, rate-limited (10/15min/IP). Same body as
  /quote plus guestName/guestEmail/guestPhone/notes. Re-validates
  everything server-side and creates the Booking row.
- POST  /api/auth/login — now rate-limited (5/15min/IP) and logs every
  outcome (login_success, login_failed, admin_login_denied, rate_limit_hit)
  to SecurityLog via services/securityLog.js.
- GET   /api/admin/security-logs — super-admin only. Query params:
  ?page= (default 1), ?eventType= (default "all"). Returns
  { success, data: { logs, page, pageSize, totalCount, totalPages }, message }.

DATA BACKUP / DISASTER RECOVERY NOTE (not yet implemented — infra decision,
not code):
Getting into the app (even as super_admin) does NOT automatically wipe the
database — data loss only happens if the attacker's access lets them run
actual DELETE/DROP operations (e.g. a leaked SUPABASE_SERVICE_ROLE_KEY, or
a SQL injection bypassing Prisma). RLS + never exposing the service role key
to the client are the main defenses against that.

=== PROCESS: Nightly Database Backup (implements protocol Rule 40) ===
Step 1 : GitHub Actions runs .github/workflows/database-backup.yml on its own
         schedule (18:00 UTC / 2:00 AM PHT) — entirely separate infrastructure
         from the app's hosting, so this never competes with live traffic
Step 2 : The workflow installs postgresql-client (for pg_dump), then runs
         `npm run backup`, which executes scripts/runBackup.js
Step 3 : runBackup.js creates a BackupLog row with status "running", then
         shells out to `pg_dump` against DIRECT_URL (session pooler — pg_dump
         needs a stable session the transaction pooler doesn't reliably give)
Step 4 : The dump is gzipped in memory, then uploaded to Cloudflare R2
         (services/r2.js) AND Google Drive (services/googleDrive.js)
         independently — one destination failing does not stop the attempt
         at the other
Step 5 : The same BackupLog row is updated with status "success" (if at
         least one destination succeeded) or "failed" (if both failed),
         plus file size, both destination links, and any error message
Step 6 : Super-admin reviews backup history at /superAdmin/backups — a
         strictly READ-ONLY page (GET /api/admin/backup-logs); there is
         intentionally no "Run Backup Now" button anywhere in the app —
         a manual run is triggered via GitHub Actions' own "Run workflow"
         button on database-backup.yml, never through this app itself

FILE MAP additions (Backups):
- prisma/schema.prisma — BackupLog model (status, fileSizeBytes, r2Key/r2Url,
  driveFileId/driveViewLink, errorMessage, startedAt, completedAt).
- services/r2.js — Cloudflare R2 upload helper (S3-compatible client).
- services/googleDrive.js — Google Drive upload helper via a Service

- scripts/runBackup.js — the standalone backup script itself. NEVER

9. COMMON DEBUG POINTS
- "pg_dump: command not found" when testing scripts/runBackup.js locally:
  install the postgresql-client package for your OS — pg_dump is a system
  binary, not an npm package, so `npm install` alone will never provide it.
- Google Drive upload fails with a 404/permission error: the target folder
  was not shared with the service account's email
  (GOOGLE_SERVICE_ACCOUNT_EMAIL) as an Editor — a service account has no
  Drive storage of its own and can only write into folders explicitly
  shared with it (see services/googleDrive.js header comment).
- A BackupLog row stuck on status "running" forever: the GitHub Actions
  run crashed or was cancelled mid-script before reaching the final
  prisma.backupLog.update() call — check the workflow's run log in the
  GitHub Actions tab for the actual error.
- If visitor pages 404: confirm folder is app/visitor/ (not Visitor/ or visitors/).
- If styles missing: confirm globals.css and mediaQueries.css are imported in app/layout.jsx.
- If /api/admin/* routes return 401 for a logged-in admin: confirm the "session" cookie
  actually has role "super_admin" — requireSuperAdmin() in services/adminSession.js
  rejects anything else, and middleware.js's matcher (["/superAdmin/:path*",
  "/api/admin/:path*"]) blocks unauthenticated requests before the route even runs.
- If a cancelled booking's dates don't reopen on the visitor site: check
  GET /api/bookings/dates — it only expands bookings with status: "confirmed", so a
  successful cancel (status -> "cancelled") should free those dates on next fetch.
- If "Book Now" 404s: confirm app/visitor/booking/page.jsx still exists — Header.jsx
  links directly to /visitor/booking.
- If "Login" link is missing from the Header: check components/shared/Header.jsx for
  the headerLoginLink (desktop) and headerMobileLoginLink (mobile) elements, both
  pointing to /superAdmin/login.
- If Sidebar/AdminHeader show up on the login page: confirm dashboard and the root
  /superAdmin redirect live under app/superAdmin/(protected)/ — that route group is
  what keeps app/superAdmin/login/ (a sibling folder) from inheriting the Sidebar/
  AdminHeader layout.
- If the super-admin "Super Admin" quick-fill button logs in with a password that
  doesn't match SEED_ADMIN_PASSWORD: the DEMO_SUPER_ADMIN_PASSWORD constant in
  app/superAdmin/login/page.jsx is just a hardcoded convenience string — it must be
  kept in sync by hand with SEED_ADMIN_PASSWORD in .env.local, they are not read
  from the same source.
- Admin accounts are NOT a Prisma-managed "users" table — Supabase Auth's built-in
  auth.users table is the source of truth for email/password; admin_profiles only
  stores role + fullName keyed to that same auth.users id. Password mismatches are
  fixed by re-running `npx prisma db seed`, which re-syncs the Auth user's password
  to SEED_ADMIN_PASSWORD every time it runs (see prisma/seed.js seedSuperAdmin()).
- If Booked Dates or the Reserve Your Villa picker show "No dates are booked yet."
  when bookings should exist: confirm `npx prisma db seed` has been run (it seeds
  sample bookings via seedBookings()) and that GET /api/bookings/dates returns
  success: true in the browser network tab.
- If the homepage loads scrolled down to the Booked Dates / Reserve Your Villa
  area instead of the Hero: check that BookedDatesSection.jsx and
  DateCarousel.jsx use the track-only centerCardInTrack() scrollTo helper on
  mount, never scrollIntoView() — scrollIntoView also scrolls the page's
  vertical axis to bring an off-screen section into view, which is what
  caused this bug originally.

=== PROCESS: Real Visitor Booking Flow (replaces the old static /visitor/booking placeholder) ===
Step 1 : Visitor reaches /visitor/booking either via Header's "Book Now" link
         (no query param) or DateCarousel's "Continue with this date" link
         (?checkin=YYYY-MM-DD, pre-fills the check-in field)
Step 2 : BookingFormClient loads booking rules (GET /api/booking-rules, public
         subset of the super-admin's BookingRules row) and all active rooms
         (GET /api/rooms) — only booking types the admin enabled
         (allowOvernightStay/allowDayTour/allowNightTour) appear as pills
Step 3 : Selecting a room (overnight only) triggers GET
         /api/rooms/{roomId}/availability for that room's already-booked +
         blackout dates
Step 4 : A debounced effect POSTs the current form values to
         /api/bookings/quote, which calls services/bookingPricing.js's
         validateAndQuoteBooking() — the same function the final create
         route uses — so the previewed price/rule-violation always matches
         what submit will do
Step 5 : On submit, POST /api/bookings re-runs validateAndQuoteBooking()
         server-side (never trusts the earlier quote alone), rate-limited to
         10/15min per IP via services/rateLimit.js, then creates the Booking
         row with the computed totalAmount/depositAmount
Step 6 : On success, the form is replaced with a confirmation panel showing
         the room, dates, total, deposit due, and cancellation policy —
         all sourced from the created booking's quote object, not hardcoded

DEBUG POINTS:
- "This room fits up to N guest(s)" / "requires a minimum of N night(s)" errors
  that seem wrong: services/bookingPricing.js takes the TIGHTER of the global
  BookingRules row and the selected Room's own minNightsPerBooking/
  maxNightsPerBooking — a room override can be more restrictive than the
  resort-wide default, never less.
- Known limitation: there is a small race window between the /quote preview
  and the final POST /api/bookings create where two guests could both pass
  validation for the same room/dates before either row is written (no DB-level
  exclusion constraint on date ranges yet). Low risk at this traffic scale;
  add a Postgres exclusion constraint or wrap validate+create in one
  transaction with SELECT ... FOR UPDATE if this becomes a real conflict.
- "Last-minute"/"group" discount fields exist on BookingRules but have no
  dedicated admin-configurable threshold day count for "last-minute" —
  services/bookingPricing.js hardcodes that window to 3 days
  (LAST_MINUTE_WINDOW_DAYS). Add a real field to BookingRules if this needs
  to be admin-configurable.
