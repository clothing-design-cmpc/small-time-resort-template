=== PROJECT: Villa Azure Resort ===

1. PROJECT NAME & PURPOSE
Villa Azure Resort is a private resort web application. Current phase
scaffolds the VISITOR master template (public-facing site) first, with
a SUPER ADMIN account to be scaffolded next. The visitor site follows
the section order defined in the resort visitor master template plan:
Hero, About, Rooms & Villas, Amenities, Resort Shop (browse-only, no
cart/checkout), Activities/Experiences, Gallery, Testimonials, Location,
Contact/Inquiry, Footer. Events & Functions and Spa & Wellness are
intentionally left out for now.

Progress: Hero (done), About (done). Next: Rooms & Villas.

2. TECH STACK
- Next.js 16.2.x (App Router, Turbopack)
- JavaScript (no TypeScript)
- React 19.2.x
- CSS Modules / plain CSS (no Tailwind)
- axios (installed, for client-side calls to external APIs)
- Backend service: Supabase (connected — @supabase/supabase-js, direct + session pooler)

3. ACCOUNT TYPES
- visitor    — public, no auth required (scaffolded)
- superAdmin — protected, auth required (not yet scaffolded)

4. DATABASE OVERVIEW
Supabase Postgres, schema managed via Prisma (prisma/schema.prisma) --
NEVER the Supabase SQL Editor. Tables: rooms, amenities, store_products,
bookings, admin_profiles. Prisma 7 note: connection URLs are NOT in schema.prisma --
they live in prisma.config.mjs (CLI: db push/generate/seed, uses
DIRECT_URL) and services/prisma.js (app runtime, uses DATABASE_URL via
the @prisma/adapter-pg driver adapter -- Prisma 7 requires an adapter,
plain `new PrismaClient()` with no adapter will throw at runtime).
Workflow: edit schema.prisma -> npx prisma db push -> npx prisma generate.
RLS/policies applied via prisma/enableRls.js (run once after first db
push). Seed data via prisma/seed.js (npx prisma db seed) -- also creates
the super-admin Auth user from SEED_ADMIN_EMAIL / SEED_ADMIN_PASSWORD.
Env keys required: NEXT_PUBLIC_SUPABASE_URL, NEXT_PUBLIC_SUPABASE_ANON_KEY,
SUPABASE_SERVICE_ROLE_KEY, DATABASE_URL, DIRECT_URL (in both .env and
.env.local -- Prisma CLI/config reads .env, Next.js app reads .env.local),
SEED_ADMIN_EMAIL, SEED_ADMIN_PASSWORD.

5. DATA MODELS OVERVIEW
- Room           -- name, slug (unique), description, pricePerNight, capacity, imageUrl, isActive, sortOrder
- Amenity        -- name, description, icon, isActive, sortOrder
- StoreProduct   -- name, description, price, category, imageUrl, isActive, sortOrder
- Booking        -- roomId (optional FK -> Room), guestName, checkInDate, checkOutDate
                    (checkOutDate is exclusive -- standard hotel convention), status
                    (confirmed | cancelled). Powers the Booked Dates section and the
                    Reserve Your Villa date picker -- both read the same
                    GET /api/bookings/dates endpoint instead of a hardcoded date list.
- AdminProfile   -- id (matches a Supabase Auth user UID), fullName, role, isOwner. The actual
                    email/password for every admin account lives in Supabase Auth's
                    built-in auth.users table (not managed by Prisma); admin_profiles
                    only stores role/profile metadata keyed to that same user id.
                    isOwner is separate from role -- every admin account defaults to
                    role "super_admin" regardless of who they are, so isOwner is what
                    actually distinguishes the resort owner from any other staff
                    account that gets dashboard access later. Gates the Vault
                    Passphrase settings page (app/superAdmin/(protected)/settings/
                    vault-passphrase/), which reveals the hidden vault recovery
                    URL (hash-derived, changes on every rotation) -- something
                    that should stay known to the owner alone.
                    prisma/seed.js sets isOwner: true on the one account it creates.

8. API ENDPOINTS
- POST  /api/auth/login  — body { email, password }; verifies against
  Supabase Auth + admin_profiles, sets the "session" HttpOnly cookie.
- POST  /api/auth/logout — clears the "session" cookie.
- GET   /api/bookings/dates — public; no input. Returns
  { success, data: { bookedDates: ["YYYY-MM-DD", ...] }, message }.
  Expands every confirmed Booking's [checkInDate, checkOutDate) range
  server-side and returns a deduplicated, sorted list.
- GET   /api/admin/bookings — super-admin only. Returns
  { success, data: { bookings: [...] }, message } — every Booking row
  (confirmed + cancelled) including room.name.
- PATCH /api/admin/bookings/{id} — super-admin only. Sets that booking's
  status to "cancelled". No body required.
- GET   /api/booking-rules — public. Read-only subset of the super-admin's
  BookingRules row (nights range, advance window, enabled booking types,
  tour pricing, deposit %, cancellation terms).
- GET   /api/rooms/{roomId}/availability — public. Returns that room's
  unavailableDates (booked + blackout, merged) plus its capacity/nights bounds.
- POST  /api/bookings/quote — public. Body: { roomId, bookingType,
  checkInDate, checkOutDate, numberOfGuests }. Validates against
  BookingRules + room overrides and returns a price breakdown WITHOUT
  saving anything. Returns 400 with a guest-facing message on any
  rule violation.
- POST  /api/bookings — public, rate-limited (10/15min/IP). Same body as
  /quote plus guestName/guestEmail/guestPhone/notes. Re-validates
  everything server-side and creates the Booking row.
- POST  /api/auth/login — now rate-limited (5/15min/IP) and logs every
  outcome (login_success, login_failed, admin_login_denied, rate_limit_hit)
  to SecurityLog via services/securityLog.js.
- GET   /api/admin/security-logs — super-admin only. Query params:
  ?page= (default 1), ?eventType=, ?deviceType=, ?country= (all default
  "all"). Returns { success, data: { logs, page, pageSize, totalCount,
  totalPages }, message }.
- GET   /api/admin/security-logs/geo-summary — super-admin only. No
  filters (always reflects full log history). Returns
  { heatmap: [{country, countryCode, count}] (top 12), countries: [...] }
  — powers both the Geo Heatmap and the Country filter's option list.
- GET   /api/admin/security-logs/export?format=csv|json — super-admin
  only. Same eventType/deviceType/country filters as the main route,
  unpaginated (capped at 10,000 rows). Streams a downloadable file with
  Content-Disposition: attachment. Logs its own admin_action row.

DATA BACKUP / DISASTER RECOVERY NOTE (not yet implemented — infra decision,
not code):
Getting into the app (even as super_admin) does NOT automatically wipe the
database — data loss only happens if the attacker's access lets them run
actual DELETE/DROP operations (e.g. a leaked SUPABASE_SERVICE_ROLE_KEY, or
a SQL injection bypassing Prisma). RLS + never exposing the service role key
to the client are the main defenses against that.

=== PROCESS: Nightly Database Backup (implements protocol Rule 40) ===
Step 1 : GitHub Actions runs .github/workflows/database-backup.yml on its own
         schedule (18:00 UTC / 2:00 AM PHT) — entirely separate infrastructure
         from the app's hosting, so this never competes with live traffic
Step 2 : The workflow installs postgresql-client (for pg_dump), then runs
         `npm run backup`, which executes scripts/runBackup.js
Step 3 : runBackup.js creates a BackupLog row with status "running", then
         shells out to `pg_dump` against DIRECT_URL (session pooler — pg_dump
         needs a stable session the transaction pooler doesn't reliably give)
Step 4 : The dump is gzipped in memory, then uploaded to Cloudflare R2
         (services/r2.js) AND Google Drive (services/googleDrive.js)
         independently — one destination failing does not stop the attempt
         at the other
Step 5 : The same BackupLog row is updated with status "success" (if at
         least one destination succeeded) or "failed" (if both failed),
         plus file size, both destination links, and any error message
Step 6 : Super-admin reviews backup history at /superAdmin/backups, and can
         also start a run early with the "Run Backup Now" button - this
         calls POST /api/admin/backup-logs/trigger, which uses
         services/github.js to remotely fire a workflow_dispatch on
         database-backup.yml. The pg_dump itself still only ever runs on
         GitHub's runner - the button never runs it inside this app.

=== PROCESS: Import SQL to Fix Database (manual restore) ===
Step 1 : Super-admin picks a .sql/.sql.gz file on /superAdmin/backups and
         confirms the destructive-action modal
Step 2 : POST /api/admin/sql-import uploads the raw file to Cloudflare R2
         under sql-imports/, creates a SqlImportLog row (status "running"),
         then calls services/github.js to dispatch
         .github/workflows/database-restore.yml with { sql_file_url,
         import_log_id }
Step 3 : The workflow runs scripts/runRestore.js on GitHub's own runner -
         downloads the file, gunzips it if needed, and applies it with
         `psql --single-transaction --set ON_ERROR_STOP=1` against
         DIRECT_URL so a mid-file failure rolls back instead of leaving
         the database half-restored
Step 4 : runRestore.js updates the SqlImportLog row to "success" or
         "failed" (+ errorMessage) when done
Step 5 : Super-admin sees the result in the import history table beneath
         the upload control on the same Backups page

=== PROCESS: 3-Gatekeeper Breach Response (Task 3) ===
Three existing detection mechanisms in this app were wired into one
shared breach-response pipeline instead of building new detectors:
  Gatekeeper 1 - login brute force (services/rateLimit.js trips on
                 5 failed attempts / 15 min at POST /api/auth/login)
  Gatekeeper 2 - SQL injection pattern detected (services/
                 sqlInjectionGuard.js, checked on login AND on
                 POST /api/bookings)
  Gatekeeper 3 - anomalous super-admin login (services/securityLog.js's
                 built-in impossible-travel / new-device detector,
                 checked after a successful login_success)

Step 1 : One of the three trigger points above fires and calls
         services/breachResponse.js -> triggerGatekeeperBreach()
Step 2 : blockIp() (services/ipBlock.js) writes a BlockedIp row for the
         offending IP - SKIPPED for Gatekeeper 3 only, since that gate
         fires after a correct password was already entered and
         auto-blocking that session's IP would risk locking the real
         super-admin out of the recovery page too
Step 3 : A BreachEvent row is created (gatekeeper, ipAddress, details)
Step 4 : SystemSettings.breachLockdown + maintenanceMode are flipped on
         with the breach message - every visitor page now renders
         components/shared/BreachLockdownScreen.jsx (full takeover, no
         Header/Footer/content) instead of MaintenanceBanner's lighter
         banner-over-a-working-site treatment
Step 5 : services/github.js dispatches database-backup.yml immediately
         (same workflow the Backups page's nightly schedule + "Run
         Backup Now" already use - Rule 40.1's decoupled-from-live-
         traffic guarantee is preserved, this never runs pg_dump inside
         the request)
Step 6 : services/emailAlert.js emails the super-admin via EmailJS's
         REST API (server-side call, not the client-only SDK) - see
         that file's header comment for the required EmailJS dashboard
         template + env vars
Step 7 : proxy.js checks BlockedIp on EVERY request from here on
         (visitor + super-admin + API routes alike) and returns a flat
         403 with no explanation to any IP found there
Step 8 : Super-admin sees a persistent red BreachAlertBanner on every
         /superAdmin/* page (components/superAdmin/BreachAlertBanner.jsx)
         linking to the hidden recovery page
Step 9 : Super-admin opens the hidden recovery page at whatever URL
         computeVaultUrlSlug() (services/vaultAuth.js) currently
         resolves to — /system-vault/<7 hex chars derived from a hash
         of the live passphrase hash>, NOT a fixed slug. The dynamic
         route lives at app/system-vault/[vaultSlug]/, and any URL
         with the wrong slug 404s via notFound() before anything else
         is checked. This page requires NO super_admin "session"
         cookie at all — proxy.js's HIDDEN_RECOVERY_PATH_PREFIX
         constant exists only so proxy.js recognizes the route family,
         it never gates it. The vault's own login chain is standalone:
         factor 1 is the vault passphrase (VAULT_PASSPHRASE_HASH /
         SystemSettings.vaultPassphraseHash, services/vaultAuth.js) at
         this slug's /login; factor 2 is a 6-digit emailed OTP
         (services/vaultOtp.js) at this slug's /otp. Only once BOTH
         are satisfied ("vaultSession" cookie with otpVerified: true)
         does the super-admin see the incident, upload the pre-breach
         .sql from Google Drive/R2 (reuses the existing useSqlImport
         hook + sql-import pipeline unchanged), and click
         "End Lockdown"
Step 10: PATCH /api/admin/breach resolves the BreachEvent and flips
         breachLockdown + maintenanceMode back off - the website is
         live again. This route (and the full-detail branch of its GET)
         requires ONLY requireVaultSession() - no super_admin session
         is checked or required on this path at all. The bannerOnly
         branch of GET (used by BreachAlertBanner on every normal
         /superAdmin/* page) is the one part of this route that still
         requires requireSuperAdmin() - it returns the current
         vaultRecoveryPath alongside the lockdown flag, so the
         banner's link is never stale after a passphrase rotation

- GET /api/admin/breach?bannerOnly=true - super-admin only, no vault
  session needed. Returns { success, data: { breachLockdown,
  activeBreach: { gatekeeper, createdAt } | null, vaultRecoveryPath },

  recentBreaches }, message }.

  lockdown, returns { success, data: null, message }.

  ("Lock Vault" button) without touching the regular admin session.
- POST /api/admin/vault-otp - standalone, requires a passphrase-only
  vaultSession. Generates + emails a 6-digit code, hashes it into
  VaultOtp. Rate limited same ceiling as vault-login.
- PATCH /api/admin/vault-otp - standalone. Body { code }. Verifies
  against the stored hash, re-issues "vaultSession" with
  otpVerified: true on match.

=== PROCESS: Real Visitor Booking Flow (replaces the old static /visitor/booking placeholder) ===
Step 1 : Visitor reaches /visitor/booking either via Header's "Book Now" link
         (no query param) or DateCarousel's "Continue with this date" link
         (?checkin=YYYY-MM-DD, pre-fills the check-in field)
Step 2 : BookingFormClient loads booking rules (GET /api/booking-rules, public
         subset of the super-admin's BookingRules row) and all active rooms
         (GET /api/rooms) — only booking types the admin enabled
         (allowOvernightStay/allowDayTour/allowNightTour) appear as pills
Step 3 : Selecting a room (overnight only) triggers GET
         /api/rooms/{roomId}/availability for that room's already-booked +
         blackout dates
Step 4 : A debounced effect POSTs the current form values to
         /api/bookings/quote, which calls services/bookingPricing.js's
         validateAndQuoteBooking() — the same function the final create
         route uses — so the previewed price/rule-violation always matches
         what submit will do
Step 5 : On submit, POST /api/bookings re-runs validateAndQuoteBooking()
         server-side (never trusts the earlier quote alone), rate-limited to
         10/15min per IP via services/rateLimit.js, then creates the Booking
         row with the computed totalAmount/depositAmount
Step 6 : On success, the form is replaced with a confirmation panel showing
         the room, dates, total, deposit due, and cancellation policy —
         all sourced from the created booking's quote object, not hardcoded

=== PROCESS: Reseller License Check (owner-only feature, not client-facing) ===
Step 1 : Every request to a matched route hits middleware.js first
Step 2 : middleware.js calls checkLicense(hostname) from services/licenseGuard.js
Step 3 : licenseGuard.js sends { license_key: RESORT_LICENSE_KEY, domain: hostname }
         to a Postgres RPC function (validate_license) hosted on a SEPARATE
         Supabase project ("License Manager") that only the owner controls —
         not this project's own Supabase
Step 4 : The RPC checks if the key exists, is "active", and if the domain
         matches what's on record for that key. Returns { valid, reason }
Step 5 : Result is cached in-memory for 6 hours to avoid hitting the
         license server on every page load
Step 6 : If invalid -> redirect to /license-invalid (plain, non-technical
         notice). If the license server is unreachable/erroring -> fails
         OPEN (site stays up) so a temporary outage never locks out a
         paying client; the failure is still console.error'd for review
Step 7 : If a client resells the template on an unauthorized domain, the
         RPC call reports the mismatched domain, giving the owner
         visibility via the (not yet built) License Manager dashboard

MULTI-POINT ENFORCEMENT (defense in depth, added after middleware-only
version): the same checkLicense() is also called directly, via the
requireLicensedRequest(request) helper, inside:
  - app/api/bookings/route.js  (POST — booking creation)
  - app/api/auth/login/route.js (POST — super-admin login)
This means removing the license block from middleware.js alone is no
longer enough to disable enforcement — a developer would have to also
find and remove it from each of these route handlers independently,
since both revenue-generating actions (taking a booking, signing in)
check it themselves. All three call sites share the same in-memory
cache in services/licenseGuard.js, so this does NOT triple the number
of validation calls to the license server.
